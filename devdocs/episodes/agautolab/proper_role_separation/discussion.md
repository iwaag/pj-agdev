# proper role separation — 論点整理 — 2026-08-08

出発点は [braindump.md](braindump.md)。agentifyエピソード
([../agentify/report.md](../agentify/report.md)) を経た現状の設計が、当初の
構想からずれ始めているという感覚の分析。

## 構想と現状のずれ

| | 構想 | 現状 |
|---|---|---|
| autolabエージェントの役割 | クライアント(人間/プライムエージェント)と作業者の**仲介役** | **リードエンジニア** |
| 知っていること | 要望、作業サイクルの回し方(計画→実装→報告→次の計画)、報告が要望から逸脱していないかの確認方法 | 上記に加えて、契約(README)・受け入れテストの設計と執筆、委譲先を打ち負かす敵対的テスト設計 |
| コーディングエージェントの役割 | **作業者かつ設計者**。要望だけを受け取り、計画を自分で立て、実装し、報告する | 単純実装マシン。確定済みのgoal・gate失敗・NOTESだけを見てテストをパスさせる |

ずれの物証:

- `agautolab/agent/CHARTER.md` の Rule 3 は「contract(README・受け入れ
  テスト・scaffolding)のseed」をautolabエージェントに明示的に許可している。
- `agautolab/AGENT_GUIDE.md` の「Seeding a job from scratch」は README と
  受け入れテストの執筆を**管理層の手順として制度化**している。
- agentify report は self-authored acceptance gates(RNG注入、
  `getTickInterval()` の grep テスト等)を最大の成果として称えているが、
  これはまさにリードエンジニアの仕事。

## 根本原因 — ドリフトは機械の構造から来ている

原因はエージェントの振る舞いではなく **autolab本体(toolbelt)のジョブ契約**。

- job.yaml は「実行前に確定した `goal`(契約として書け、と指示)と
  決定論的なシェルコマンドの `gates`」を要求する。
- コーディングエージェントは `cwd=target/` で外が見えず、goal・gate失敗・
  NOTES 以外の入力を持たない。計画を立てたり検証方法を提案する席がない。
- つまり**計画・設計・検証基準の策定をコーディング実行の前に誰かが
  済ませておく構造**であり、その「誰か」の席にautolabエージェントが
  座らされた。agentifyは制御構造を反転したが、toolbeltのインターフェイスは
  「テストを渡されてパスさせる機械」前提のままなので、上に乗るエージェントは
  必然的にリードエンジニア化する。

## 構想に戻す方向性

機械より先に**契約の流れ**を変える。

1. **goal にはユーザー要望をほぼそのまま流す。** autolabエージェントが要望を
   技術契約に翻訳する工程をやめる。
2. **計画と検証基準の提案をコーディングエージェント側の最初の成果物にする。**
   イテレーション1の出力 = PLAN.md + 自前の受け入れテスト案。
   autolabエージェントはそれを「要望から逸脱していないか」の観点で
   レビューして承認/差し戻しする。
3. **書くのはやめるが、読むのはやめない。** CHARTER Rule 3 を
   「実装もテストも書かない。委譲先の計画とゲートを要望に照らして審査する」
   に差し替える。これなら「自分に甘いゲート」問題への防衛線(監査)は
   仲介役の職掌のまま維持できる。
4. autolabエージェントに残る知識は構想どおりのものだけになる:
   サイクルの進行、逸脱チェック、complete/blocked の判断、予算管理、
   クラッシュ復旧。

## 留保 — 現行設計に不利な証拠はまだない

agentify の結果は現行設計の**成功**を示している: 敵対的ゲートは実際に機能し、
恐れていた「甘いゲート」は起きなかった。ただしそれは「管理層がテストを書く
設計が有効」の証明であって、「その分離が仲介役設計より優れている」の証明では
ない。Snake規模ならコーディングエージェント自身に検証基準を考えさせても
同等に機能した可能性が高く、**比較対照はまだ取れていない**。
リードエンジニア/作業者の分離にメリットを感じないというのは現時点では経験則
であり、機械の証拠に変える余地がある。

## 未解決の論点

- **ゲートの決定論性をどこまで保つか。** コーディングエージェントが提案した
  テスト案を、autolab の決定論的 gate 機構にそのまま載せるのか
  (承認後に job.yaml へ反映?)、それとも gate 機構自体に「提案→承認」の
  フェーズ概念が要るのか。
- **自己承認リスクの移動。** ゲート authorship を作業者側に移すと、
  「自分が書いたテストを自分がパスする」構図になる。仲介役の審査
  (要望とのトレーサビリティ確認)だけで十分か、外部検証
  (agentifyで使った Playwright 監査のような)を標準装備にするか。
- **既存プロジェクトへの適用。** braindump の構想は「新規リポジトリ立ち上げ」
  と「既存プロジェクト上でのコーディングエージェント起動」の両方を含む。
  現行の job/target 構造は新規前提が強く、既存リポジトリでの seed レス運用は
  未設計。
- **プライムエージェントとの接続。** 依頼元が agdevworld のプライム
  エージェントになったとき、要望の受け渡し形式(MISSION.md 相当)と
  報告の返し方はどうするか。

## 次のエピソード候補

同一ミッション(例: agentify の Snake)で、ゲート authorship を
コーディングエージェント側に移した版を走らせ、現行設計と比較する。
経験則を証拠に変える A/B が取れる最小構成。うまくいけば CHARTER /
AGENT_GUIDE をこの方向に書き換える。
